# 引言

`call/cc`（全称 *call-with-current-continuation*，「以当前延续调用」）是 Scheme 传统中最强大、也最令人畏惧的控制操作符之一。人们常说它是「美化的 goto」，这个说法可以照字面检验。C 的 `goto` 只能跳到写死在代码里的标签。如果标签本身是一个值，可以存进变量、作为返回值，就成了**一等标签**（first-class labels）。从一等标签出发，离 `call/cc` 还有多远？

# 一等标签

设想我们有一等标签：

```racket
(define-type ⊥ (∪))  ; 空类型：没有构造子，没有值
(: goto  (→ Label ⊥))
(: label (→ Label))
```

`(label)` 捕获程序中的当前位置，返回一个 `Label` 值。`(goto l)` 跳回 `l` 被创建的位置。返回类型 $⊥$（bottom）表示 `goto` 永远不会返回到调用者：它把控制转移到了别处。

>**注意：** 代码在 `#lang typed/racket/no-check` 下运行：类型标注使用 Typed Racket 语法，但不会被类型检查器验证。这些标注是描述预期契约的设计文档，并非机器检查的断言。

## 循环

```racket
(let ([x 0])
  (define loop (label))
  (set! x (add1 x))
  (when (< x 7) (goto loop))
  (displayln x))
;; 打印：7
```

我们在循环体顶部捕获一个标签。每次 `(goto loop)`，执行就从 `(label)` 调用之后恢复。可变变量 `x` 记录我们已经执行了多少次迭代。

## 提前返回

```racket
(define (mul . r*)
  (define first? #t)
  (define result (*))       ; 乘法单位元 = 1
  (define ret (label))
  (when first?
    (set! first? #f)
    (for ([r (in-list r*)])
      (when (zero? r)
        (set! result r)
        (goto ret))
      (set! result (* result r))))
  result)
```

这里的 `ret` 就是一个「返回标签」。如果在列表 `r*` 中遇到零，直接短路跳到末尾。布尔标志 `first?` 用来区分初始进入和通过 `goto` 跳回来的情况。

## 标签的问题

注意两个例子都依赖**修改可变状态**（`set!`）来在跳转之间传递信息。`(goto loop)` 时，标签本身不携带任何数据，所以我们不得不通过副作用来进入正确的状态。第二个例子中的标志 `first?` 与乘法无关：它存在的唯一目的就是区分「我们是第一次运行，还是刚刚跳回来？」

# 从标签到延续：`cc` 操作符

一等标签的根本限制在于：`goto` 是一张单程票，不带任何载荷。要避免修改状态，我们需要向跳转目标发送一个值。这就是**延续**（continuation）的核心思想。

`(label)` 第一次被求值时，我们希望它返回一个「回调」：一个以后可以调用的函数，带着一个值跳回去。当调用那个回调时，`(label)` 应该「再次返回」，这次返回的就是传入的那个值。

于是这个操作符的返回值有两种可能：

- 类型为 $p → ⊥$ 的延续：接受类型为 $p$ 的值且永不返回的函数（它跳回捕获点）。
- 类型为 $p$ 的值，在延续被调用时收到。

我们把这个操作符叫做 `cc`（*current-continuation* 的缩写）：

```racket
(: cc (∀ (p) (→ (∪ p (→ p ⊥)))))
(define (cc)
  (define v* #f)
  (define l (label))
  (if v*
      (apply values v*)
      (λ vs (set! v* vs) (goto l))))
```

从代码看，`v*` 标志控制分支：首次进入时 `v*` 为 `#f`，`(label)` 先捕获当前位置，随后 `(if v* ...)` 走入 else 分支，返回一个函数（也就是延续）。日后调用它时，它把参数存入 `v*` 并跳回捕获点；控制回到 `(if v* ...)`，此时 `v*` 不再是 `#f`，走 then 分支，`(cc)` 返回之前存入的那个值。

>**注意：** `cc` 的内部实现仍然使用了 `label`、`goto` 和 `set!`，但这些机制现在被封装起来了。`cc` 的使用者永远不需要触碰可变状态。该实现对多值做了处理（`v*`、`apply values`）；本文所有类型标注均省略多值情形以求清晰。

## 再写 `mul`

```racket
(define (mul . r*)
  (define result (cc))
  (if (real? result)
      result
      (for/fold ([res (*)] #:result (result res))
                ([r (in-list r*)])
        (if (zero? r)
            (result r)
            (* res r)))))
```

第一次求值 `(cc)` 时，`result` 绑定到一个延续（一个函数）。因为延续不是 `real?`，我们进入 `else` 分支并开始折叠。如果遇到零，调用 `(result r)`，触发延续：控制跳回求值 `(cc)` 的位置，现在 `result` 绑定到 `r`（一个实数）。进入 `then` 分支，立即返回。如果没有遇到零，`for/fold` 的 `#:result` 子句在折叠结束后调用 `(result res)`，同样触发延续，`result` 绑定到累积乘积 `res`，从 `then` 分支返回。两条路径都通过延续 `result` 汇合，不需要可变状态，也不需要标志。

# 消除分支：`call/cc`

`cc` 消除了可变状态，但带来了新的要求：**分支**。每次调用 `(cc)` 的返回值都有两种可能，程序员必须区分收到的是哪种情况。在提前返回的例子中，我们用 `(real? result)` 来分离值和延续。这能工作，但又多了一件需要操心的事。能不能把分支也一并消除？

不再返回联合类型让调用者去分支，而是让调用者传入一个函数 `proc`，直接把延续作为参数交给它。分支发生在操作符内部，对用户不可见：

```racket
(: call/cc (∀ (p) (→ (→ (→ p ⊥) p) p)))
(define (call/cc proc)
  (define v* (cc))
  (if (list? v*)
      (apply values v*)
      (proc (λ vs (v* vs)))))
```

用户传入一个函数 `proc`，它接收一个类型为 $p → ⊥$ 的延续作为参数。在 `proc` 内部调用这个延续，会中止 `proc` 并向 `call/cc` 的调用者传递一个类型为 $p$ 的值；如果 `proc` 正常返回而不调用延续，就直接使用它的返回值。`list?` 负责区分这两种情况：首次调用 `(cc)` 时，`v*` 绑定到延续（一个函数），不是列表，走 else 分支把它封装后交给 `proc`。交给 `proc` 的包裹 `(λ vs (v* vs))` 用 rest 形式的 `vs` 将参数收集成列表，再以列表调用 `cc` 的延续。`cc`「再次返回」时带着这个列表，此时 `v*` 绑定到列表，所以 `(list? v*)` 为真，`(apply values v*)` 解包返回。

很多时候传给 `call/cc` 的 `proc` 就是个用来命名当前延续的 lambda。定义一个语法糖来省去这层包装：

```racket
(define-syntax-rule (let/cc k body ...)
  (call/cc (λ (k) body ...)))
```

> **练习：** 用 `let/cc` 定义 `call/cc`。

## 更一般的延续类型

传给 `proc` 的逃逸延续类型为 $p → ⊥$。但考虑这个函数：

```racket
(: absurd (∀ (q) (→ ⊥ q)))
(define absurd (case-λ))
```

`absurd` 的类型为 $⊥ → q$，对任意 $q$ 成立：从空类型可以推出任何东西。因为 `case-λ` 没有任何子句，它是一个永远不可能被调用的函数（没有可匹配的情况），这一定义完全合法。

现在，给定一个类型为 $p → ⊥$ 的延续 `k`，复合函数 `(compose absurd k)` 的类型为 $p → q$，对任意 $q$ 成立。操作上，这个复合的行为与 `k` 本身**完全一样**：用一个类型为 $p$ 的值调用它会触发 `k`，控制跳走，永远到不了 `absurd`。但从类型系统的角度看，返回类型现在是任意的 $q$ 而不是 $⊥$。

这意味着我们可以把逃逸延续视为具有更一般的类型 $p → q$ 而非 $p → ⊥$。在这个视角下，`proc` 的类型为 $(p → q) → p$，`call/cc` 的类型变成：

$$((p → q) → p) → p$$

这比原来的类型更一般：令 $q = ⊥$ 就恢复原来的版本。在有类型的语言里，这个更一般的类型很常见，例如 Haskell 的 `callCC :: ((a -> m b) -> m a) -> m a`，延续的返回类型可以是任意的 `m b`。但对于本文来说，$p → ⊥$ 的版本更具揭示性：它直接展示了延续*是*什么（一个接受 $p$ 且永不返回的函数），不需要通过 `absurd` 的额外泛化步骤。

## 那条看不见的延续

还有另一种方式来解读 `call/cc` 的类型。回忆一下，`k` 和 `(compose absurd k)` 在操作上完全一样，因为 `k` 永不返回，所以 `absurd` 永远不会被执行到。`call/cc` 本身也有一个类似的等价关系：

```racket
(call/cc proc)
(call/cc (λ (k) (k (proc k))))
```

两者是一样的：第二个版本中，`proc` 的结果显式地通过 `k` 路由；第一个版本中，同样的事情也在发生。`cc` 在 `(define v* (cc))` 处捕获延续，这个延续接收一个值后做什么？执行 `if`，返回 `call/cc` 的结果，然后继续 `call/cc` 调用之后的代码。`cc` 捕获的延续就是 `call/cc` 的延续。而 `proc` 在 else 分支的尾位置，所以它的延续也是同一个 `k`。包裹不改变任何东西：无论 `proc` 的返回值走哪条路，都通过同一个 `k` 传递，显式调用 `(k (proc k))` 和正常返回 `(proc k)` 汇入同一个出口。因此 `proc` 的类型是 $(p → ⊥) → ⊥$：它接受一个延续，并通过那个延续传递其结果。于是 `call/cc` 也可以读作：

$$((p → ⊥) → ⊥) → p$$

输入一个借延续来交付结果的计算，从中把结果取出来。

# 从 `call/cc` 定义标签

令 $p = \text{Label}$，`call/cc` 交给 `proc` 的延续类型就是 $\text{Label} → ⊥$，恰好是一个标签。标签因此可以直接由 `call/cc` 定义：

```racket
(define-type Label (→ Label ⊥))
(define (goto l) (l l))
(define (label) (call/cc goto))
```

$\text{Label} = \text{Label} → ⊥$ 是一个递归类型：标签是一个接受标签且永不返回的函数。`(label)` 捕获当前延续，把它当作标签立即跳转过去：一次到自身的原地跳转，所以延续收到的就是它自身。后续的 `(goto l)` 调用 `l` 并传入 `l`，跳回 `(label)` 被求值的位置，再次返回 `l`。

三者也可以按另一个顺序互相定义，先从标签得到 `call/cc`，再由它得到 `cc`：

```racket
(define (call/cc proc)
  (define v* #f)
  (define l (label))
  (if v*
      (apply values v*)
      (proc (λ vs (set! v* vs) (goto l)))))

(define (cc) (call/cc values))

(define (label) (cc))
(define (goto l) (l l))
```

无论按哪个顺序，三种表述都能互相定义，在**表达能力上等价**。

# 比较

|                    | 一等标签 (`goto` + `label`)        | 值与延续的联合 (`cc`)       | 高阶回调 (`call/cc`)                             |
|--------------------|------------------------------------|-----------------------------|--------------------------------------------------|
| **涉及的类型**     | 只有 `Label`                       | 联合类型 $p ∪ (p → ⊥)$      | 高阶：$((p → ⊥) → p) → p$ 或 $((p → ⊥) → ⊥) → p$ |
| **需要可变状态？** | 是：必须用 `set!` 在跳转间传递信息 | 否                          | 否                                               |
| **需要手动分支？** | 否                                 | 是：必须区分 $p$ 和 $p → ⊥$ | 否                                               |

三种风格能做到的事没有区别，力量的来源也是同一个：跳转目标成为了值。在 C 中，label 是代码中的固定位置，不能存入变量、不能传给函数、不能作为返回值。label 成为值的那一刻，`goto` 就获得了 `call/cc` 的全部力量。这一步之后的一切都是易用性方面的取舍：每种风格为更方便地管理同一种能力付出不同的代价（可变状态、分支、高阶类型）。

# 深层的逻辑

三种风格的差别，最后都落在了类型上。比较表的第一行里有联合类型，也有高阶类型；单是 `call/cc` 一个操作符，就写出了三种签名，而且每一种都成立。这些操作符的实现用到了 `label`、`goto` 和 `set!`，签名里却一样也看不到，只用到 $→$、$⊥$、$∪$ 三样东西。写 `absurd` 时我们还顺口说了一句「从空类型可以推出任何东西」，这已经是逻辑里的说法了。把这些签名放在一起：

```racket
(: cc      (∀ (p)   (→ (∪ p (→ p ⊥)))))
(: call/cc (∀ (p)   (→ (→ (→ p ⊥) p) p)))
(: call/cc (∀ (p q) (→ (→ (→ p q) p) p)))
(: call/cc (∀ (p)   (→ (→ (→ p ⊥) ⊥) p)))
(: absurd  (∀ (q)   (→ ⊥ q)))
```

如果把 $⊥$ 读作假，$→$ 读作蕴含，$∪$ 读作析取：

| 类型                | 像什么       |
|---------------------|--------------|
| $p ∪ (p → ⊥)$       | 排中律       |
| $((p → ⊥) → p) → p$ | Clavius 律   |
| $((p → q) → p) → p$ | Peirce 律    |
| $((p → ⊥) → ⊥) → p$ | 双重否定消除 |
| $⊥ → q$             | 爆炸原理     |

五个签名，对上了五条有名字的定律。这只是字面上的相像，还是经得起检验？

## 从 $⊥$ 出发

在这个类比中，没有值的空类型 $⊥$ 应该对应假：不存在该类型的表达式。如果这个类比成立，那么 $p → ⊥$ 就对应逻辑中的否定：给定 $p$ 的证明，推出假。而延续的类型正是 $p → ⊥$。

验证一下。$⊥$ 的否定是 $⊥ → ⊥$。恒等函数就具有这个类型。更一般地，`absurd` 为任意 $q$ 提供了 $⊥ → q$。所以假的否定是非空的：它是真的，逻辑中 $¬⊥$ 也确实为真。这个类比目前站得住脚。

那么非空类型的否定呢？类型 $\text{Real} → ⊥$ 是一个接受实数且永不返回的函数。我们能构造出具有该类型的表达式吗？只用普通的 λ 和函数调用，写不出来：函数体最终要交出一个值，而 $⊥$ 没有值可交。前面见到的延续，都是 `cc`、`call/cc` 这样的控制操作符在运行时捕获出来的，不是用 λ 写出来的。

所以对于任何非空的类型 $p$，只用纯函数，类型 $p → ⊥$ 是空的：真命题的否定是假。这个类型就是**否定** $¬p$，每个延续都是一个否定：

```racket
(define-type (¬ p) (→ p ⊥))
```

非空意味着为真，空意味着为假。为一个类型写出表达式，就是证明对应的命题。

## 从类型到逻辑

「非空即真」的读法能推广到我们用过的其他类型构造子吗？假设有两个表达式 $x$ 和 $y$，类型分别是 $p$ 和 $q$。从这个设定出发，我们可以构造出：

1. $p → q$ 类型的表达式 `(λ (x) y)`：给定一个 $p$，就能产出一个 $q$。也就是说：如果 $p$ 成立，那么 $q$ 成立。这是**蕴含**，写作 $→$。

2. $p × q$ 类型的表达式 `(values x y)`：把 $x$ 和 $y$ 打包在一起。也就是说：$p$ 和 $q$ 同时成立。这是**合取**，写作 $∧$。

3. $p ∪ q$ 类型的表达式：$x$ 本身就可以视为这个类型（$y$ 也一样）。也就是说：$p$ 或 $q$ 成立。这是**析取**，写作 $∨$。（Typed Racket 的 `∪` 是普通的并集，并非真正的不相交联合；程序员必须自行用 `real?` 这样的谓词来保证不相交性。）

合取和析取各有一个单位元。合取的单位元是 $⊤$，对应 Typed Racket 中的 `(Values)` 类型：它只有一个值 `(values)`，而且对任意类型 $p$，`(Values p (Values))` 和 `(Values (Values) p)` 都等价于 $p$（$p ∧ ⊤ = ⊤ ∧ p = p$）。析取的单位元是 $⊥$，也就是 `(∪)` 类型：它没有任何值，而且对任意类型 $p$，`(∪ p (∪))` 和 `(∪ (∪) p)` 都等价于 $p$（$p ∨ ⊥ = ⊥ ∨ p = p$）。

每个类型构造子都对应一个逻辑连接词。类型是命题，表达式是证明，构造程序就是构造证明。这个对应关系有一个名字：**Curry-Howard 对应**。

有了 $¬$ 和 $∨$，上面的类型签名变成：

$$\texttt{cc} : p ∨ ¬p \qquad\qquad \texttt{absurd} : ⊥ → q$$

$$\texttt{call/cc} : (¬p → p) → p \quad\text{或}\quad ((p → q) → p) → p \quad\text{或}\quad ¬¬p → p$$

而 $\text{Label} = \text{Label} → ⊥$ 变成 $\text{Label} = ¬\text{Label}$：一个自身否定的类型。

前面表格的第二列不必再说「像」：$p ∨ ¬p$ 是排中律，$(¬p → p) → p$ 是 Clavius 律，$((p → q) → p) → p$ 是 Peirce 律，$¬¬p → p$ 是双重否定消除（*Double Negation Elimination*，DNE），$⊥ → q$ 是爆炸原理。我们写的类型签名，每一项都对应着一条逻辑定律；除了爆炸原理，其余几条都只在经典逻辑中成立。

## 对应关系在哪里失效

Curry-Howard 对应在纯粹的全函数语言（如 Agda 和 Coq）中是精确的：对任意非空的 $p$，$¬p$ 确实是空的。真实的编程语言打破了这一点。

考虑 `(define (loop) (loop))`。它的类型是 $→ ⊥$，即 $⊤ → ⊥ = ¬⊤$：真的否定。在纯粹理论中，$¬⊤$ 应该是空的，因为真不可反驳。但 `(loop)` 是这个类型下合法的表达式，只不过永不终止。在非全函数语言中，合法的表达式不一定终止，因此并非每个表达式都是证明。

类似地，内置的 `exit` 的类型是 $\text{Byte} → ⊥ = ¬\text{Byte}$。借助 `exit`，我们可以为任意 $p$ 构造 $¬p$：`(λ (_) (exit 0))`。任何真命题的否定都变成了非空。

还有第三种失效。我们的类型 $\text{Label} = ¬\text{Label}$ 是一个自身否定的类型。把它读作命题：如果它为真（非空），它的否定就为真，所以它为假。如果它为假（空），它的否定就平凡地非空（正如 `absurd` 填充了 $⊥ → p$），但 $¬\text{Label} = \text{Label}$，所以它又变成了真。

这就是**说谎者悖论**：「这句话是假的。」它无法被一致地赋予真假值。在 Agda 和 Coq 这样的一致类型论中，**正性**条件禁止这类定义：一个类型不能出现在自身定义中的否定位置（$→$ 的左侧），从而排除了自指式的否定。（更强的*严格*正性条件进一步禁止嵌套否定位置的出现，如 $(T → A) → A$；我们的 $\text{Label} = \text{Label} → ⊥$ 在第一层就已违反。）Racket 没有这个限制。悖论是合法的，我们可以构造 Label 类型的值。同样的结构也出现在硬件中：环形振荡器（奇数个反相器首尾相连，最简单的情形是三个）永远振荡；理想化的单反相器版本 $Q = ¬Q$ 是同一个不动点方程。

每种情况下，严格的 Curry-Howard 解读都失效了：本应为空的否定类型有了值，本应非法的自指类型变得合法。我们把这个对应关系当作结构性的指引：类型的结构映射到逻辑连接词的结构，即便严格的逻辑解读不再精确。

## 分水岭

在引入 `cc` 和 `call/cc` 之前，我们拥有的一切（函数、积、联合、$⊤$、$⊥$）都属于**直觉主义逻辑**：构造性类型系统所自然栖居的逻辑。那么 `cc` 和 `call/cc` 到底添加了什么？

我们有四种与否定交互的方式。其中两种只需要普通函数：

**矛盾律：** 把一个 $¬p$ 和一个 $p$ 放在一起，得到 $⊥$。

```racket
(: apply-cont (∀ (p) (→ (¬ p) p ⊥)))
(define (apply-cont k . v*) (apply k v*))
```

这就是函数调用。我们给它起了个名字 `apply-cont`，因为在当前的设定中延续恰好是函数。但「向延续传递一个值」本身是一个独立的概念：延续换一种表示，它就不再只是函数调用。

**双重否定引入**（*Double Negation Introduction*，DNI）是同一个操作，只是参数顺序不同。`apply-cont` 接收延续和值，而 DNI 先接收值，返回一个等待延续的 $¬¬p$：`(curryr apply-cont)`。这是一个纯粹的 lambda，不需要任何控制操作符。

两者都是**构造性有效的**。另外两种则需要捕获当前延续：

**排中律：** 产出一个 $p ∨ ¬p$。这是 `cc`。

**双重否定消除：** 从一个 $¬¬p$ 中提取一个 $p$。这是 `call/cc`。

|                | 构造性                                  | 经典                                    |
|----------------|-----------------------------------------|-----------------------------------------|
| $¬p$ 遇上 $p$  | **矛盾律**：`apply-cont`（函数调用）    | **排中律**：`cc`（捕获延续）            |
| $¬¬p$ 遇上 $p$ | **双重否定引入**：柯里化的 `apply-cont` | **双重否定消除**：`call/cc`（捕获延续） |

*消耗*一个否定（把 $¬p$ 和 $p$ 放在一起，或者把 $p$ 包进 $¬¬p$）是构造性的。*产出*一个否定（通过 `cc` 得到 $p ∨ ¬p$，或者通过 `call/cc` 从 $¬¬p$ 中提取 $p$）是经典的。分界线就在消耗与产出之间。

> **练习：** *实质条件* $¬p ∨ q$ 是经典逻辑中 $p → q$ 的另一种编码。试着实现 `material->procedure : (¬p ∨ q) → p → q` 和 `procedure->material : (p → q) → ¬p ∨ q`。你会发现其中一个方向需要 `cc`，是哪一个？

# 代入排中律

到目前为止，对应关系一直是从程序读向逻辑：先写出操作符，再认出它的类型是哪条定律。它也可以反过来用。

逻辑里，一条定律对任何命题都成立，把一个具体的命题代进去，就得到一条新的定理。在程序里，这一步就是给操作符的类型参数指定一个具体的类型。

代入哪条定律？直觉主义定律只涉及引入 `cc` 之前就有的函数、多值和联合，它们的实例用 λ 本来就写得出来。经典定律不同，它们的实例一般要靠 `cc` 或 `call/cc` 才能给出。代入经典定律，就可能得到 λ 写不出的操作符，而它会做什么，可以先从命题的形状读出来。其中最直接的一条是排中律，它就是 `cc` 的类型 $p ∨ ¬p$。

## 代入 $\text{Label}$

排中律 $p ∨ ¬p$ 的两个分支，一个是 $p$，一个是 $¬p$：一真一假。但如果代入的类型让真假变成同一个东西呢？更进一步：既然两个分支是同一个类型，我们何必再区分它们？

既真又假，这正是说谎者悖论，我们熟悉的 $\text{Label}$。放宽排中律对不相交的要求，把 $\text{Label}$ 代入 $p$：

$$\text{Label} ∨ ¬\text{Label} = \text{Label} ∨ \text{Label} = \text{Label}$$

一切坍缩为 `Label`。$\text{Label}$ 是**否定的不动点**：它的反驳就是它自己。特别地，**`goto` 本身就是一个 `Label`**：

$$\text{Label} → ⊥ = ¬\text{Label} = \text{Label}$$

之前所有的例子中，我们都是 `goto` 配 `label` 使用：

```racket
(goto (label))
```

但既然每个 $\text{Label}$ 同时也是一个合法的 $¬\text{Label}$，没有什么能阻止我们把*任意*标签传给任何其他标签：

```racket
((label) (label))
```

在类型层面上，「跳转目标」和「跳转指令」没有区别：它们是同一种东西。这种自指式的坍缩不是 bug，它是延续令人费解的那些行为的源头。

### 阴阳谜题

让标签直接作用于标签，就得到 David Madore 的阴阳谜题：

```racket
(let ([yin (label)])
  (display #\@)
  (let ([yang (label)])
    (display #\*)
    (yin yang)))
```

输出：

```
@*@**@***@****@...
```

程序里没有循环，没有计数器，也没有 `set!`：只有两次 `(label)`、两次 `display` 和一次调用。输出却是一道无限增长的阶梯，每一轮都比上一轮多打印一个 `*`。多出来的那个 `*`，记在了哪里？

#### 追踪谜题

给每个延续一个唯一的名字（`k0`、`k1`、`k2`……），让每次 `apply-cont` 都记录哪个延续被应用于哪个：

```racket
(define n -1)
(define (cc)
  (set! n (+ n 1))
  (let/cc k
    (define l (cons k (string->symbol (string-append "k" (number->string n)))))
    (apply-cont l l)))
(define (apply-cont kl l)
  (display (list (cdr kl) (cdr l)))
  (display #\tab)
  ((car kl) l))
```

这里的延续是函数和名字的 `cons` 对，不能再直接调用。「向延续传递一个值」也就不再只是函数调用：`apply-cont` 先拆开这个对，记下名字，再调用里面的函数。`cc` 构造延续，`apply-cont` 消费延续，谜题改用这两个函数来写：

```racket
(let ([kn (cc)])
  (displayln #\@)
  (let ([kn+1 (cc)])
    (displayln #\*)
    (apply-cont kn kn+1)))
```

输出：

```
(k0 k0)	@
(k1 k1)	*
(k0 k1)	@
(k2 k2)	*
(k1 k2)	*
(k0 k2)	@
(k3 k3)	*
(k2 k3)	*
(k1 k3)	*
(k0 k3)	@
...
```

#### 读矩阵

把追踪排列成矩阵（行按参数标签索引，列按目标标签索引）：

```
	k0	k1	k2	k3	...
k0	@
k1	@	*
k2	@	*	*
k3	@	*	*	*
...
```

矩阵的每一行对应追踪输出中的一个段落（从一次 `k0` 被调用到下一次 `k0` 被调用之间）。但执行顺序是每行从右向左：追踪里的 `(k2 k3)*`、`(k1 k3)*`、`(k0 k3)@` 对应第 `k3` 行从右往左扫过的 `*`、`*`、`@`。每行 $n$ 打印一个 `@` 和 $n$ 个 `*`。这个模式来自：

1. **`k0` 打印 `@`** 并捕获一个新的延续 `kn+1`。
2. **`kn+1` 打印 `*`** 并跳向 `kn`。
3. **每个 `kn`** 被调用时，收到最近捕获的延续 `k` 作为参数。

之所以能级联，是因为每个延续都「记得」下一步要跳向哪个 `kn`，形成一条链，每经过一次 `k0` 就多一个链节。

#### 用函数重写

这三条规律只涉及延续之间谁调用谁、传的是什么。照着它们，把每个延续直接写成一个函数：跳向一个延续，就是调用它；捕获一个新延续，就是定义一个新函数。

```racket
(define (k0 kn)
  (display #\@)
  (define (kn+1 k)
    (display #\*)
    (kn k))
  (kn+1 kn+1))
(k0 k0)
```

`k0` 打印 `@`，定义一个新函数 `kn+1` 打印 `*` 并委托给 `kn`，然后用自身调用 `kn+1`：

- 第一次调用时，`kn = k0`。打印 `@` 后，创建一个新闭包 `kn+1`（我们叫它 `k1`），它打印 `*` 并委托给 `k0`。然后 `(kn+1 kn+1)` 用自身调用 `k1`：`k1` 打印 `*` 并调用 `(k0 k1)`。
- 现在回到 `k0`，此时 `kn = k1`：打印 `@`，创建另一个新闭包 `k2`，它打印 `*` 并委托给 `k1`，然后调用 `(k2 k2)`。`k2` 打印 `*` 并调用 `(k1 k2)`；`k1` 打印 `*` 并调用 `(k0 k2)`。
- 以此类推：每次经过 `k0` 都给委托链多加一环。

运行它，输出同样是 `@*@**@***@****@...`。

这段代码里没有 `label`、`cc`，也没有 `set!`。原来由 `cc` 捕获的延续，现在都成了显式传递的参数：`k0` 收到 `kn`，`kn+1` 收到 `k`，每一次跳转都是把延续交给下一个函数的尾调用。这种把延续作为参数传递的写法，叫做**延续传递风格**（*Continuation-Passing Style*，CPS）；把程序改写成这种写法，就是 **CPS 变换**。

反过来看，原来的谜题就是这组**互递归调用**，只是其中的延续由 `(label)` 在运行时捕获，而不是作为参数传进来。回忆我们说过的 $\text{Label} = ¬\text{Label}$，它是说谎者悖论，一个既不能判真也不能判假的命题。阴阳谜题就是那个悖论作为程序运行起来的样子：永不终止地振荡，永远无法落定为真或为假。

## 代入 $¬q$

$\text{Label}$ 是一个极端的例子。它是自身的否定，排中律二者择一的结构在它身上坍缩成了一个类型；一致的类型论甚至不允许定义它。退一步，不要求类型否定自己，只要求它是另一个类型的否定。代入 $¬q$：

$$¬q ∨ ¬¬q$$

两个分支还在。$¬q$ 是延续，我们已经很熟悉了。$¬¬q$ 呢？逻辑上它是双重否定，`call/cc` 的类型可以视为 $¬¬q → q$。如果 `cc` 直接把双重否定交给了我们，那它意味着什么？

### 程序的类型

假设我们的语言有 `call/cc` 但没有内置的 `exit`。我们可以模拟一个：把整个程序包在 `call/cc` 里，捕获的延续就成为退出通道。

```racket
(call/cc (λ (exit) ...程序体...))
```

在程序体内，调用 `(exit 0)` 就跳出整个计算。参数 `exit` 的类型是 $\text{Byte} → ⊥$，即 $¬\text{Byte}$：一个接受退出码且永不返回的函数。传给 `call/cc` 的函数 `(λ (exit) ...)` 接收这个 $¬\text{Byte}$ 并运行。它的类型是什么？它接受一个 $¬\text{Byte}$，然后……它返回吗？如果程序体调用了 `(exit 0)`，控制跳走，这个函数永不返回。如果程序体正常结束，返回值流向……`exit`，因为那就是延续。无论哪条路，结果都通过 `exit` 传递。这个函数的类型是 $¬\text{Byte} → ⊥$，即 $¬¬\text{Byte}$。

真实的操作系统也是这样运行程序的。启动一个程序时，OS 提供一个退出通道，进程通过它交回状态码（显式地通过系统调用，或者隐式地通过从 `main` 返回），然后 OS 接管。这就是 $¬¬\text{Byte} → \text{Byte}$：OS 提供一个延续，程序体通过它传递一个字节，OS 拿回一个值。运行一个程序，就是一次 DNE。

消除的对象，那个 $¬¬\text{Byte}$，正是程序本身。程序是一个 $¬¬q$：它期望得到一个退出通道，一个来自未来的延续。OS 运行它的时候满足这个期望，消除双重否定，提取出结果。

程序记录了一系列运算，本质上是一种推迟计算。推迟计算的另一种常见形式是 thunk。

### Thunk

一个 thunk $⊤ → q$ 把计算包起来，按需运行。它和 $¬¬q$ 是同一回事吗？

不完全是。在纯函数式语言中，thunk 和类型为 $q$ 的普通值无法区分。但一旦我们允许副作用，thunk 就变得必要了：它们**推迟**计算，使得结果反映调用时而非定义时的状态。

```racket
(define b 111)
(: f (→ Real))
(define (f) (* 1 b))
(displayln (f))    ; => 111
(set! b 222)
(displayln (f))    ; => 222
(set! b 333)
(displayln (f))    ; => 333
```

每次调用 `f` 都看到 `b` 的*当前*值。Thunk 不缓存任何值：每次调用，都是向当前状态发起的一次实时查询。

但 thunk 适应调用点的*一切*，不仅仅是变量环境。它还运行在调用者的**求值上下文**中：`parameterize` 绑定、`dynamic-wind` 的进出守卫、异常处理器，以及其他属于延续而非变量环境的一切。

```racket
(define a (make-parameter 1))
(define b 111)
(: f (→ Real))
(define (f) (* (a) b))
(displayln (f))        ; => 111
(set! b 222)
(displayln (f))        ; => 222
(parameterize ([a 2])
  (displayln (f)))     ; => 444，不是 222！
```

当我们在 `(parameterize ([a 2]) ...)` 内部调用 `(f)` 时，参数 `a` 是 `2`，所以我们得到 $2 × 222 = 444$。Thunk 适应调用点的一切：变量环境，求值上下文，全盘接受。它完全不记得自己是在哪里定义的。

能不能反过来？记住定义时的上下文，冻结它，但变量还是用调用点的。Thunk 做不到。

### 冻结上下文

回到 $¬q ∨ ¬¬q$。`(cc)` 第一次返回时，交出的是捕获点的延续；在这个类型下，它等待的是一个 $¬q$，所以它的类型是 $¬¬q$。把一个 $¬q$ 交给它，控制跳回 `(cc)` 被求值的地方，`(cc)` 第二次返回，交出的正是这个 $¬q$。

跳回捕获点，也就回到了那里当时的求值上下文，而不是调用点的。这正是 thunk 做不到的那种冻结。

我们其实已经会构造 $¬¬q$ 了：`(λ (exit) body)`，其中 `body` 显式使用 `exit`。但单纯的 λ 没有冻结行为，它像 thunk 一样适应调用点的一切。需要把 λ 构造的 $¬¬q$ 用 `cc` 包一层，让 `cc` 来产出这个 $¬¬q$：

```racket
(define-type (¬¬ q) (¬ (¬ q)))

(: wait/fc (∀ (q) (→ (¬¬ q) (¬¬ q))))
(define (wait/fc kk)
  (define first? #t)
  (: k (∪ (¬ q) (¬¬ q)))
  ;; 首次：(cc) 返回这个位置作为延续；k : ¬¬q
  ;; 重入：(cc) 返回刚刚传递到这里的值；k : ¬q
  (define k (cc))
  (unless first? (kk k))
  (set! first? #f)
  k)
```

`wait/fc`（*wait-for-future-continuation* 的缩写）是这样工作的：首次调用 `(cc)` 时，`first?` 为 `#t`，跳过 `unless`，将 `first?` 设为 `#f`，返回一个 $¬¬q$。之后有人用某个延续调用这个 $¬¬q$，控制跳回 `(define k (cc))`，`k` 被重新绑定为那个延续。`first?` 现在为 `#f`，进入 `unless` 分支，以 `k` 为参数调用 `kk`。`kk` 在过去的上下文中运行，结果通过 `k` 跳走传出。

放宽一步：允许 `proc` 正常返回，返回值隐式地通过 `k` 流出。这和 `call/cc` 的 `proc` 在尾位置返回时走同一条 `k`，是同一个道理。`wait/fc` 的类型变为 $(¬q → q) → ¬¬q$：

```racket
(: wait/fc (∀ (q) (→ (→ (¬ q) q) (¬¬ q))))
(define (wait/fc proc)
  (define first? #t)
  (define k (cc))
  (unless first? (call-with-values (λ () (proc k)) k))
  (set! first? #f)
  k)
```

把 `wait/fc` 和 `call/cc` 放在一起：

| 操作符    | 类型                            | `proc` 收到什么 |
|-----------|---------------------------------|-----------------|
| `call/cc` | $(¬q → q) → q$ 或 $¬¬q → q$     | **当前**延续    |
| `wait/fc` | $(¬q → q) → ¬¬q$ 或 $¬¬q → ¬¬q$ | **未来**延续    |

`call/cc` 交给 `proc` 的，是调用点已经存在的延续；`wait/fc` 交给 `proc` 的，要等以后触发 $¬¬q$ 的人提供。一个捕获当前，一个等待未来。

把 thunk 例子里的 `f` 换成 `wait/fc` 做出的 $¬¬\text{Real}$：

```racket
(define a (make-parameter 1))
(define b 111)
(: f (¬ (¬ Real)))
(define f (wait/fc (λ (_) (* (a) b))))
(displayln (call/cc f))        ; => 111
(set! b 222)
(displayln (call/cc f))        ; => 222
(parameterize ([a 2])
  (displayln (call/cc f)))     ; => 222，不是 444！
```

每次 `(call/cc f)` 都是一次穿过曾经求值上下文的往返。调用点的 `parameterize` 是不可见的：`(a)` 总是 `1`，因为它在 `(cc)` 首次调用的地方求值。但 `b` 反映当前值，因为 `b` 属于变量环境，不属于求值上下文。

每次进入 `f` 都**恢复**同一个动态范围：同样的 `parameterize` 绑定，同样的异常处理器，同样的 `dynamic-wind` 守卫，无论调用点长什么样。但每次进入也**继承**最新的变量状态：`b` 把当前值从一次调用带到下一次，因为可变变量活在被捕获的范围之外。

程序有同样的分裂。每次运行被恢复的是可执行映像：指令在程序被构建的那一刻就固定了。跨运行持续存在的是进程之外的世界：文件、环境变量、命令行参数。两者冻结的东西不同（可执行文件冻结的是指令序列，`wait/fc` 冻结的是动态范围），但结构上的轴是同一条：创建一次，多次重入，不因重入而改变。在这个意义上，`proc` 是源代码，`wait/fc` 是构建步骤，产出的 $¬¬q$ 是可执行文件，用 `call/cc` 运行它就是操作系统提供退出延续。

值、thunk 和 $¬¬q$ 在这条轴上各占一个位置：

| 概念          | 关联于 | 每次进入恢复的         | 跨进入持续存在的       |
|---------------|--------|------------------------|------------------------|
| 值 $q$        |        | 无：立即可用           | 无：立即可用           |
| Thunk $⊤ → q$ | $q$    | 无：适应一切           | 一切：变量环境与上下文 |
| $¬¬q$         | $q$    | 求值上下文（动态范围） | 变量环境（可变状态）   |

### 组合冻结上下文

初版 `wait/fc` 的类型是 $¬¬q → ¬¬q$：输入和输出同类型，一个 `wait/fc` 的输出可以直接作为另一个 `wait/fc` 的输入。嵌套之后，每一层冻结的上下文都有自己的边界，边界穿越可以用 `dynamic-wind` 观察。调用 `(dynamic-wind enter thunk exit)` 求值 `thunk`，但在进入前运行 `enter`，在退出后运行 `exit`。关键点：这些守卫不仅在正常求值时触发，在延续跳转穿越边界时（无论是跳入还是跳出）也会触发。每当一次跳转进入某个 `dynamic-wind` 的范围，它的 `enter` 守卫触发；每当一次跳转离开，它的 `exit` 守卫触发。

```racket
;; 时刻 1：在上下文 C1 中，冻结最内层计算
(define W1
  (dynamic-wind
    (λ () (displayln "C1: enter"))
    (λ () (wait/fc
           (λ (fc)
             (displayln "reached the frozen context C1")
             (fc 'hello))))
    (λ () (displayln "C1: exit"))))

;; 时刻 2：在上下文 C2 中，把 W1 包裹进第二层冻结
(define W2
  (dynamic-wind
    (λ () (displayln "C2: enter"))
    (λ () (wait/fc W1))
    (λ () (displayln "C2: exit"))))

;; 时刻 3：触发链条
(displayln (call/cc W2))
```

输出：

```
C1: enter
C1: exit
C2: enter
C2: exit
C2: enter
C2: exit
C1: enter
reached the frozen context C1
C1: exit
hello
```

创建阶段，每一层的守卫各触发一次：进入、捕获、退出。两个冻结上下文随后进入休眠状态，W1 保存在 W2 内部。

触发点把当前延续交给 W2，W2 跳回 C2 捕获的上下文：`C2: enter` 第二次触发。在那里，`wait/fc` 的重入立刻把延续转手给 W1，再次跳转：`C2: exit`，然后 `C1: enter`。输出中连续的 `C2: enter` / `C2: exit` 就是穿过中间层：进入，接过接力棒，退出。最内层的 `proc` 终于运行，看到未来延续 `fc`，调用 `(fc 'hello)`：`C1: exit` 触发，`'hello` 回到触发点。

未来延续像接力棒一样穿过每一层冻结，每次边界跨越都触发对应的 `dynamic-wind` 守卫。输出就是接力棒的行程记录。

> **练习：** 把触发点本身也包裹进第三个 `dynamic-wind`，带上自己的进入和退出守卫，在运行前预测完整输出。注意：*跳出*触发点的上下文也会触发守卫。

---

# 结论

比较一节把三种风格的力量归于同一步：跳转目标成为值。这个值的类型是 $¬p$。只用 λ 和函数调用，写不出非空 $p$ 的 $¬p$，`cc` 和 `call/cc` 交出的延续都是在运行时捕获的。分水岭一节的表格沿着同一条线分成两列：`apply-cont` 和 DNI 消耗手里已有的否定，只需要普通函数；`cc` 和 `call/cc` 产出一个新的否定，必须捕获。

程序在操作系统面前也处在这条线上。它是一个 $¬¬\text{Byte}$，等待的那条 $¬\text{Byte}$ 不由它自己写出，而是在启动时由操作系统交给它。`wait/fc` 做出的 $¬¬q$ 同样在等待，只是交来延续的换成了日后的调用者。

## 未解的线索

但我们小心避开了一个问题。编程语言建立在**构造性**的基础之上：Curry-Howard 对应把程序与直觉主义证明配对，而在直觉主义逻辑中，排中律不是定理。然而我们一直在愉快地使用排中律、Clavius 律和 DNE，仿佛它们是天经地义的。

这怎么可能？一个构造性语言如何支持经典推理？

阴阳谜题的 CPS 分解提供了一条线索。当我们只用纯 lambda 和函数调用（没有 `call/cc`、没有 `goto`、没有可变状态）重写谜题时，表达能力没有任何损失。经典的控制流仍然存在，只是被**换了一种方式编码**：作为显式的延续传递。在证明论中，这种编码叫做**否定翻译**（negative translation）；它在计算上的对应物，叫做**延续单子**。

还有另一根线头。程序类型 $¬¬\text{Byte}$ 中的 $⊥$ 不是世界的终结：进程终止后，OS 继续运行。$⊥$ 只是*这个进程*的终结，不是所有计算的终结。它是一个*相对的* bottom，不是绝对的。

如果我们能在程序*内部*拥有相对的 $⊥$ 呢？如果函数调用，而不仅仅是 OS，也能充当定界符呢？
