# 世界尽头有何物：我们早已熟知的边界

答案藏在一件你每天都在做的事里：调用一个函数时，会发生什么。

# 函数调用

第一篇里，我们用 `goto` 和 `label` 实现了提前返回：

```racket
(define (mul . r*)
  (define first? #t)
  (define result (*))
  (define ret (label))
  (when first?
    (set! first? #f)
    (for ([r (in-list r*)])
      (when (zero? r)
        (set! result r)
        (goto ret))
      (set! result (* result r))))
  result)
```

`(goto ret)` 跳到函数出口处的标签，跳过剩余的迭代。标签 `ret` 标记了函数计算的边界：它上方的一切是函数自己的工作，`goto` 跨越了这条边界。

在汇编中，也是用这两个原语实现的函数调用：调用者保存一个返回地址（`ret`），跳到函数体执行计算，计算完成后跳回来。大多数语言把 `goto` 和 `label` 藏在了内建的 `return` 后面。Racket 没有内建的 `return`，这里假想有一个，借它来改写 `mul`：

```racket
(define (mul . r*)
  (define result (*))
  (for ([r (in-list r*)])
    (when (zero? r) (return 0))
    (set! result (* result r)))
  (return result))
```

`(return 0)` 做的事情和 `(set! result r) (goto ret)` 一样：直接递交一个值给调用者，跳过了函数体内当前位置的后续计算。

# 返回答案

`goto` 版和 `return` 版的 `mul` 都借用了语言提供的跳转机制，一个用一等标签，一个用内建的 `return`。两者都是一步到位地把控制转移到函数出口。如果不用任何跳转，遇到零时的提前返回还能实现吗？

先想清楚提前返回到底意味着什么。它意味着这段计算的答案提前出现了。遇到零的那一刻，最终结果已经确定，后面再怎么乘也改变不了零。既然答案已经在手上，剩下的每一层要做的事情就只有一件：把它原样往上递，不要再拿它去参与计算。所以不需要跳转，只需要一个判断：手里这个东西是还在算的中间结果，还是已经定了的最终答案？

区分的方式很直接。用一个带类型参数的 struct 把答案标记出来：

```racket
(struct (r) ans ([a : r]) #:type-name Ans)
```

`(Ans r)` 包着一个 `r` 类型的答案。第二篇的 `ans` 装的是一张值的列表，那是为了让 `raise` 带着多个返回值跨出去；这里只需要一个答案，字段就换成了单值。`(ans 0)` 说的是「这段计算的答案是零」：裸的 `0` 是中间结果，还可以继续乘下去；`(ans 0)` 是最终答案，后续计算只需把它交出去。有了这个标记，`mul` 可以完全不跳转：

```racket
(: mul (→ Real * Real))
(define (mul . r*)
  (: real* (→ Real Real (∪ Real (Ans Real))))
  (define (real* a b)
    (if (or (zero? a) (zero? b))
        (ans 0)
        (* a b)))
  (: loop (→ (Listof Real) (∪ Real (Ans Real)) (Ans Real)))
  (define (loop r* result)
    (cond
      [(ans? result) result]
      [(null? r*) (ans result)]
      [else (loop (cdr r*) (real* (car r*) result))]))
  (ans-a (loop r* (*))))
```

```racket
> (mul 1 2 3 4)
24
> (mul 1 2 0 3 4)
0
```

看 `loop` 的三条分支。拿到一个 `ans` 就原样传递；列表空了就把累积结果包成 `ans`；否则继续迭代。三条路最终都返回 `(Ans Real)`，无一例外。

# 边界的两侧

`ans` 这个构造子出现在两处：`real*` 里遇到零，提前知道了答案；`loop` 里列表空掉，处理完所有元素。两条路都把最终结果包成 `ans`，交给外面的 `ans-a`。看 `mul` 的最后一行：

```racket
(ans-a (loop r* (*)))
```

`ans-a` 圈出了一段局部计算的范围：括号里面是 `loop` 的整段迭代，以 `(Ans Real)` 收场。`loop` 收到答案就原样返回，不拆开也不使用里面的值。到了边界之外，`ans-a` 才取出那个实数，交给调用者继续计算。

`real*` 的结果类型 `(∪ Real (Ans Real))` 把两条路径放在了一起：普通实数还能继续参与乘法，带标签的答案则直接交出。如果普通结果的类型是 `P`，整段计算的答案类型是 `a`，这两条路径就写成 `(∪ P (Ans a))`，缩写为 `Pᵃ`。上标 `a` 表示为这段计算的答案留出一条路径。在 `mul` 里，普通结果和最终答案都是实数，`(∪ Real (Ans Real))` 因而记作 `Realᵃ`。

如果 `P` 是 $⊥$ 呢？普通结果这一侧没有任何值，联合中只剩答案：

$$⊥ᵃ = (∪ ⊥ (Ans a)) = (Ans a)$$

空类型是联合的单位元。给它加上答案这条路径，得到的恰好就是答案类型；在眼前的 `mul` 里，`⊥ᵃ` 就是 `(Ans Real)`。

这个名字也对应着 `loop` 的行为。收到 `ans` 后，它不再调用 `real*`，不继续乘法，只把答案交出去。对这段局部计算来说，产出答案与终止是同一个事件。答案不会再作为普通结果参与内部的运算，`⊥ᵃ` 因而充当局部空；边界之外，`ans-a` 却能从中取出一个普通的实数，交给调用者继续使用。从内部看到的局部空，正是从外部看到的局部答案。

程序的 $⊥$ 也是一个答案：进程终止时产出 `Byte` 类型的退出码。从进程内部看，`exit` 之后不再有运算可以拿退出码继续计算；从操作系统看，退出码是一个普通的字节值，OS 拿着它继续工作。`exit` 之于进程就像 `ans` 之于 `loop`。用 `⊥ᵃ` 给这段局部计算的答案及其边界操作命名：

```racket
(define-type ⊥ᵃ (Ans Real))
(define ⊥ᵃ?   ans?)
(define a->⊥ᵃ ans)
(define ⊥ᵃ->a ans-a)
```

`a->⊥ᵃ` 就是 `ans`，`⊥ᵃ->a` 就是 `ans-a`。一个把值送进局部计算的空，另一个从空里取出答案。这对操作划出的边界有一个名字：**prompt**。用这组名字重写 `mul`：

```racket
(define-type Realᵃ (∪ Real ⊥ᵃ))

(: mul (→ Real * Real))
(define (mul . r*)
  (: real* (→ Real Real Realᵃ))
  (define (real* a b) ...)
  (: loop (→ (Listof Real) Realᵃ ⊥ᵃ))
  (define (loop r* result) ...)
  (⊥ᵃ->a (loop r* (*))))
```

有跳转的语言里，`real*` 的返回类型 `Real` 其实是 `(∪ Real ⊥)`，$⊥$ 意味着允许跳转，`return` 负责跨过边界。去掉跳转，全局的 $⊥$ 替换成局部的 $⊥ᵃ$，中间层也可能提前得到答案，这引入了分支，于是中间层的结果类型 `Real` 变成了 `Realᵃ`。第二篇的 `a->⊥` 用 `raise` 一步跨过所有中间层，`⊥->a` 用 handler 接住；把 `raise` 和 handler 拿掉，剩下 `ans` 这个 struct，每一层只能自己检查、自己往上递。

`loop` 里那个 `(⊥ᵃ? result)` 和 `mul` 要算的乘法毫无关系，纯粹是程序员额外操心的事情。第一篇里 `cc` 有过同样的问题：返回值可能是延续也可能是值，调用者必须手动分支，后来 `call/cc` 把分支藏进了操作符内部才解决。这里的 `(⊥ᵃ? result)` 检查，能不能也藏起来？

# 局部延续

全局的 $⊥$ 从来不需要 `⊥?`。第二篇的 CPS 版 `mul` 里只出现过 $⊥$、$¬p = p → ⊥$、`a->⊥`、`⊥->a` 这四样东西，没有任何检查。如果把它们全部换成局部版本，`⊥ᵃ?` 自然就不会出现。$⊥ᵃ$、`a->⊥ᵃ`、`⊥ᵃ->a` 已经有了，补上类型别名：

```racket
(define-type (¬ₐ p) (→ p ⊥ᵃ))
```

$¬ₐp$ 是**局部延续**（local continuation）：一个接受 $p$ 并产出局部答案 $⊥ᵃ$ 的函数。代入 CPS 版的 `mul`：

```racket
(: mul (→ Real * Real))
(define (mul . r*)
  (: loop/kₐ (→ (Listof Real) (¬ₐ Real) ⊥ᵃ))
  (define (loop/kₐ r* kₐ)
    (if (null? r*)
        (kₐ (*))
        (let ([r (car r*)])
          (if (zero? r)
              (a->⊥ᵃ r)
              (loop/kₐ (cdr r*) (λ (v) (kₐ (* v r))))))))
  (⊥ᵃ->a (loop/kₐ r* a->⊥ᵃ)))
```

```racket
> (mul 1 2 3 4)
24
> (mul 1 2 0 3 4)
0
```

照第二篇的写法把闭包链写出来。把 `(λ (v) (* v 3))` 记作 `mul3`，其余类推，`(mul 1 2 3 4)` 走到列表末尾时，手里的局部延续是：

```racket
(∘ a->⊥ᵃ mul1 mul2 mul3 mul4)
```

第二篇里，排在最前面的是 `a->⊥`。`a->⊥ᵃ` 扮演的角色和它一样：闭包链的底，空栈。区别在于 `a->⊥ᵃ` 只是一个普通的构造函数，不会调用语言提供的跳转机制，所以基于它构造的整条闭包链也是普通的函数，用于产出这段局部计算的答案。它们是局部计算过程中的剩余工作，局部延续恰如其名。

`loop` 每次迭代都要检查 `(⊥ᵃ? result)`，这个检查在这里消失了。CPS 把栈上的帧搬到了堆上的闭包里，所有调用都在尾位置，栈上只有一层，根本不存在需要检查的中间层。`(mul 1 2 0 3 4)` 遇到零时，手里的局部延续是 `(∘ a->⊥ᵃ mul1 mul2)`。程序没有调用它，而是越过 `mul1`、`mul2`，直接调用最前面的 `a->⊥ᵃ`：`(a->⊥ᵃ r)` 产出答案，直接返回就行。

回头看这次替换。四样东西里，$⊥$ 是其余三样共同的落点：$¬p$ 指向它，`a->⊥` 把值送进它，`⊥->a` 从它取回答案。把这个落点从 $⊥$ 换成 $⊥ᵃ$，其余三样跟着换成局部版本，代码的结构一点没变，闭包链也只是换了最前面的那一个。所有延续都落在同一个终点上，这个终点可以称为它们的**基**；这次替换，就是一次**换基**。

# 逃逸与丢弃

CPS 版的 `mul` 用局部延续正常工作了。那 `anf:eval` 呢？把 `anf:eval` 和 `cps:call/cc` 也换成局部版本：

```racket
(define (((cps f) . p*) kₐq) (kₐq (apply f p*)))
(define ((cps:call/cc cps:proc) kₐp) ((cps:proc (cps kₐp)) kₐp))
(define (anf:eval kₐkₐa) (⊥ᵃ->a (kₐkₐa a->⊥ᵃ)))
```

简单的算术照常运行：

```racket
> (anf:eval
   (anf:let* ([v (cps:+ 1 2)]
              [w (cps:* v 3)])
     (cps:+ w 100)))
109
```

但用 `cps:call/cc` 实现提前退出时，出事了：

```racket
> (anf:eval
   (cps:call/cc
    (λ (cps:return)
      (let cps:loop ([r* '(1 2 0 3 4)])
        (anf:begin
         (cps:displayln r*)
         (anf:if (cps:null? r*)
                 (cps:*)
                 (anf:let* ([r (cps:car r*)]
                            [r (anf:if (cps:zero? r) (cps:return r) (cps:id r))]
                            [r* (cps:cdr r*)]
                            [res (cps:loop r*)])
                   (cps:* res r))))))))
(1 2 0 3 4)
(2 0 3 4)
(0 3 4)
(3 4)
(4)
()
; *: contract violation
;   expected: number?
;   given: #<ans>
```

乘法收到了一个 `ans` struct，而不是数字。答案泄漏到了不该出现的地方。

问题出在 `cps:call/cc` 交给 `cps:proc` 的那个逃逸延续 `(cps kₐp)` 上。展开 `cps` 看看它做了什么：

```racket
(((cps kₐp) . p*) kₐq)  =  (kₐq (kₐp . p*))
```

`(cps kₐp)` 接收参数，调用 `kₐp` 得到结果，然后把结果传给当前延续 `kₐq`。但 `(kₐq ...)` 这一步在全局版本中从未执行过：全局延续的 `kp` 通过 `raise` 跳走，控制永远到不了 `kq`。宿主的跳转一直在替我们丢弃 `kq`，只是我们之前没注意到。

然而局部延续没有跳转行为，`(kₐp . p*)` 产出一个 `ans` 正常返回，`(kₐq ...)` 第一次真正执行了。报错信息 `expected: number? given: #<ans>` 说的就是这件事：`kₐq` 把答案当作中间值传给了乘法，乘法不认识它。

既然 `(kₐp . p*)` 已经得到了答案，直接返回就行，忽略掉 `kₐq`：

```racket
(define (((cps* kₐp) . p*) _kₐq) (apply kₐp p*))
(define ((cps:call/cc cps:proc) kₐp) ((cps:proc (cps* kₐp)) kₐp))
```

`cps*` 丢弃当前延续 `_kₐq`，用保存的 `kₐp` 直接产出答案。跳转就是替换当前延续，`goto` 和 `call/cc` 靠语言内置的机制完成替换，`cps*` 手动完成同样的事。

换上修好的 `cps:call/cc`，重新运行前面的例子，遍历在遇到零的那一步停了下来：

```racket
(1 2 0 3 4)
(2 0 3 4)
(0 3 4)
0
```

# 边界中的边界

CPS 代码中用不到 `⊥ᵃ?`。那么在整段局部计算中，和 `⊥ᵃ` 打交道的只剩 `a->⊥ᵃ` 和 `⊥ᵃ->a` 这一对函数，值进去，同一个值出来。既然中间没有人检查 `Ans` 的内部，struct 包装就是空操作，可以取平凡表示：

```racket
(define-type ⊥ᵃ Real)
(define-type (¬ₐ p) (→ p ⊥ᵃ))
(define a->⊥ᵃ values)
(define ⊥ᵃ->a values)
```

局部延续 $¬ₐp = p → Real$，一个普通函数，没有 struct，没有跳转。闭包链的底成了 `values`，写不写都一样：

```racket
  (∘ a->⊥ᵃ mul1 mul2 mul3 mul4)
= (∘ values mul1 mul2 mul3 mul4)
= (∘ mul1 mul2 mul3 mul4)
```

链上只剩那一串乘法。

回到之前报错的 `(kₐq (kₐp p))`：`(kₐp p)` 现在返回 $⊥ᵃ$，即 `Real`；`kₐq` 收到 `Real`，类型吻合。被 `cps*` 丢弃的 `kₐq` 不再需要丢弃。于是第二篇的 `cps:call/cc` 定义本来就有意义，只是捕获的不再是会跳转的延续，而是作为普通函数的局部延续：

```racket
(define ((cps:call/lc cps:proc) kₐp) ((cps:proc (cps kₐp)) kₐp))
```

`cps:call/lc`（*call with local continuation*），和 `cps:call/cc` 逐字相同。但 `(cps kₐp)` 的行为不同了：`kₐp` 这条闭包链的底不再是 `ans` 而是 `values`，那个空栈现在什么也不做，调用它执行完局部工作就正常返回，`kₐq` 接着运行。调用被捕获的延续不是跳转，而是组合，一次普通的函数调用。

把前面例子里的 `cps:call/cc` 换成 `cps:call/lc`：

```racket
(1 2 0 3 4)
(2 0 3 4)
(0 3 4)
(3 4)
(4)
()
0
```

`(cps:return r)` 没有跳出循环。和修复版相比，这里多出来的三行，正是 `cps*` 丢弃掉的那部分工作：遇到零后没有跳走，而是继续循环，将零乘进了后续的每一步，最终结果仍然是零。

而这一切成立的前提是 $⊥ᵃ$ 取了平凡表示。`cps:call/lc` 用的就是最开始 `cps:call/cc` 的定义，在 struct 表示下，就会发生之前的报错。要想在 struct 表示下也能用 `cps:call/lc`，就得把平凡表示里隐藏的那一步转换手写出来，用 `⊥ᵃ->a` 手动取出答案：

```racket
(define ((cps:call/lc cps:proc) kₐp)
  (define (kp p) (⊥ᵃ->a (kₐp p)))
  ((cps:proc (cps kp)) kₐp))
```

交给 `cps:proc` 的函数 `(λ (p) (⊥ᵃ->a (kₐp p)))`，接受一个值，沿 `kₐp` 的闭包链执行局部工作，在根部碰到 `a->⊥ᵃ`，再由外面的 `⊥ᵃ->a` 取出答案。这和 `anf:eval` 是同一个结构：

```racket
(define (anf:eval kₐkₐa) (⊥ᵃ->a (kₐkₐa a->⊥ᵃ)))
```

`a->⊥ᵃ` 和 `⊥ᵃ->a` 划出的那条边界出现在了 `call/lc` 的内部。内层有自己的 `a->⊥ᵃ`，自己的 `⊥ᵃ->a`，自己的 prompt；外层只看到一个正常返回的值。局部计算里有了局部计算。

这个结构在 `call/lc` 的内部自然出现了。如果程序员能显式地做同样的事，在局部计算里开辟新的边界，用新的 `a->⊥ᵃ` 开始一段子计算，那么 `call/lc` 捕获的闭包链就到那个新起点为止，边界限定了捕获的范围。

怎么在一段局部计算里开启另一段局部计算？`anf:eval` 已经能运行一个 CPS 计算，只是它本身还是普通函数。用 `cps` 把它带进 CPS 世界：

```racket
(define anf:reset (cps anf:eval))
```

`anf:reset` 调用 `anf:eval` 运行内层计算。`anf:eval` 为它交入新的初始局部延续；内层得到答案以后，`cps` 再把答案交给外层延续。于是内层拥有自己的起点，外层只看到一个正常返回的值。每次 `anf:reset` 都开启一段新的局部计算，在当前边界里面重新划出一条边界。内层的世界尽头，从外层看来，只是一个子计算返回了。

# 定界延续

`cps*` 把局部延续提升为具有跳转行为的延续。前面用它构建了 `cps:call/cc`：调用提升后的延续时，丢弃调用点的当前延续，改用保存的那条。

但 `cps:call/cc` 提升的是 CPS 参数 `kₐp`，即当前局部延续，它随计算不断变化。CPS 程序运行时，还有一条局部延续始终不变：`anf:eval` 在启动计算时提供的初始局部延续 `a->⊥ᵃ`。既然 `cps*` 可以提升任何局部延续，把它用在 `a->⊥ᵃ` 上：

```racket
(define cps:abort (cps* a->⊥ᵃ))
```

`cps:abort` 丢弃当前延续，把值交给初始局部延续：从闭包链的任意位置跳到底部，值成为这段局部计算的答案。回看前面 `cps:call/cc` 实现提前退出的例子：

```racket
(anf:eval
 (cps:call/cc
  (λ (cps:return)
    ...)))
```

那里 `cps:call/cc` 处于 `anf:eval` 之后的第一个位置，还没有任何绑定，当前延续就是初始局部延续 `a->⊥ᵃ`。`cps:call/cc` 交出 `(cps* kₐp)` = `(cps* a->⊥ᵃ)` = `cps:abort`。之前通过 `call/cc` 得到的 `cps:return`，现在不再需要捕获。这就是 `return`。

在函数里调用另一个函数，被调用者从自己的空栈开始执行。`anf:reset` 做的是同一件事：`anf:eval` 把 `a->⊥ᵃ` 交给内层计算 `kₐkₐa`：空栈，没有待执行工作。内层计算以它为根，通过 `anf:let*` 构造自己的闭包链；外层的 `kₐa` 没有被接入内层。`(anf:eval kₐkₐa)` 是一次非尾调用：宿主在当前帧保存了「拿到答案后调用 `kₐa`」这件待办工作。

前面说过，CPS 把栈上的帧搬到堆上的闭包里，通过尾调用推进。宿主栈不再需要为局部工作保留帧，于是可以承担定界：内层的工作由显式延续表示，外层的等待由宿主帧保存。内层完成时通过普通返回交出答案，外层拿着答案继续。这正是这篇开头描述的事情：调用一个函数时，调用者保存返回地址，函数体执行，完成后跳回来。在 `anf:reset` 内使用 `cps:abort`，就是从这次调用中 `return`。

前面 `cps:call/lc` 已经表明，被 `return` 丢弃的局部延续其实是一个普通函数：调用它就执行剩余局部工作，正常返回结果。如果主体既能取得这个函数，又能交出答案，它就可以选择调用、保存或丢弃局部延续。`cps:call/lc` 取得函数，`cps:abort` 交出答案，两者组合就是 `shift`：

```racket
(define neg²:abort (cps->neg² cps:abort))

(define-syntax-rule (anf:let/lc cps:k b* ...)
  (cps:call/lc (λ (cps:k) b* ...)))

(define-syntax-rule (anf:shift cps:k e)
  (anf:let/lc cps:k (neg²:abort e)))
```

`anf:shift` 的最后一步是 `neg²:abort`：和 `return` 一样，丢弃剩余的局部工作，把主体的结果作为局部计算的答案交出。不同的是，丢弃之前，`anf:let/lc` 先把那段工作命名为 `cps:k`，交给了主体。`shift` 就是命名了局部延续的 `return`。

前面一直称为「局部延续」的对象，由 `reset` 的边界限定范围，通常称为**定界延续**（delimited continuation）。`reset` 和 `shift` 是操作定界延续的一组接口。

`shift` 做的两件事，捕获与跳转，也可以只留下一样。如果主体捕获局部延续后又把结果交回给它，跳转就被撤销了，剩下的只是捕获：`(shift k (k e)) = (let/lc k e)`。如果主体忽略捕获的局部延续，剩下的只是跳转：`(shift _ e) = (abort e)`。反过来读这条等式，`return` 就是丢弃了局部延续的 `shift`。

```racket
(define-syntax-rule (let/lc k body) (shift k (k body)))
(define (abort . v*) (shift _ (apply values v*)))
```

## 四个例子

先用 `reset` 和 `abort` 做一次普通的调用与返回。内层计算给 `3` 加上 `2`，把答案交出来；外层拿到结果，再加上 `10`：

```racket
> (anf:eval  ;; 例 1：reset 加 abort，没有 shift
   (anf:let* ([v (anf:reset
                  (anf:let* ([x (cps:id 3)]
                             [y (cps:+ 2 x)])
                    (cps:abort y)))])
     (cps:+ 10 v)))
15
```

`(cps:abort y)` 把 `5` 交给内层的初始局部延续，结束这段计算。`anf:reset` 取出答案，让外层绑定 `v = 5`，继续计算 `10 + 5 = 15`。内层的返回没有丢弃外层的工作。

现在只改动产生 `x` 的位置，用 `shift` 捕获局部延续，但先不用它：

```racket
> (anf:eval  ;; 例 2：捕获后不使用
   (anf:let* ([v (anf:reset
                  (anf:let* ([x (anf:shift cps:k (cps:id 3))]
                             [y (cps:+ 2 x)])
                    (cps:abort y)))])
     (cps:+ 10 v)))
13
```

到达 `shift` 时，边界内等待的工作是：收到 `x`，计算 `2 + x`，再通过 `cps:abort` 交出答案。这就是 `cps:k` 保存的局部延续。外层的 `10 + v` 在 `reset` 之外，没有被捕获。

主体 `(cps:id 3)` 不使用 `cps:k`，直接以 `3` 为结果。`shift` 把它作为内层计算的答案交出，原来的加二没有执行，外层得到 `10 + 3 = 13`。这就是一次提前 `return`：`cps:k` 绑定了 `return` 每次都在丢弃的那段工作，只是这次没人使用它。

如果把这个 `3` 交给刚刚捕获的延续呢？

```racket
> (anf:eval  ;; 例 3：调用被捕获的延续一次
   (anf:let* ([v (anf:reset
                  (anf:let* ([x (anf:shift cps:k (cps:k 3))]
                             [y (cps:+ 2 x)])
                    (cps:abort y)))])
     (cps:+ 10 v)))
15
```

`(cps:k 3)` 执行保存的工作，得到 `2 + 3 = 5`。`cps:k` 来自 `call/lc`，调用它时 `⊥ᵃ->a` 包住一次局部计算并取出答案。因此里面的 `cps:abort` 交出的 `5` 会正常返回到 `shift` 的主体。

主体以这个 `5` 为结果，`shift` 再把它作为所在局部计算的答案交出。外层仍然得到 `10 + 5 = 15`，与第一例相同。`(shift k (k e))` 就是 `(let/lc k e)`，`e` 不用 `k` 时退化为 `e`，所以例三和例一是同一段计算。

调用能够返回，就可以拿着返回值继续计算。把主体改成先调用一次，再把结果交给同一个 `cps:k`：

```racket
> (anf:eval  ;; 例 4：调用被捕获的延续两次
   (anf:let* ([v (anf:reset
                  (anf:let* ([x (anf:shift cps:k
                                 (anf:let* ([r (cps:k 3)])
                                   (cps:k r)))]
                             [y (cps:+ 2 x)])
                    (cps:abort y)))])
     (cps:+ 10 v)))
17
```

第一次 `(cps:k 3)` 算出 `5`，返回后绑定给 `r`；第二次 `(cps:k r)` 把 `5` 作为输入，再做一次加二，返回 `7`。每次调用都有自己的边界，内部的 `cps:abort` 结束的是那次调用中的局部工作，主体仍然可以接着计算。

被保存的始终是同一条局部延续：第一次调用的结果，成为第二次调用的输入。两次加二完成后，主体交出 `7`，外层再加上 `10`，得到 `17`。外层的加十没有被重复执行，它一直在 `reset` 之外等待最终的答案。

四个例子展示的是同一段局部工作的三种命运：被丢弃（例 2），被调用一次（例 3），被调用两次（例 4）。例 1 没有 `shift`，那段工作照常执行，不存在丢弃或捕获的问题。`shift` 做的事情就是把这个选择权交给程序。

## 定界延续与 CPS

`shift` 能把剩余工作交给程序，但我们实现它时没有借助宿主原生的捕获。四个例子共享同一段局部工作：收到 `x`，加二，交出答案。化简后的程序里，这段工作以什么形式出现，`shift` 的主体又怎样与它对接？

例一和例三是同一段计算。`(shift k (k e)) = (let/lc k e)`，其中 `e` 没用过 `k`，`let/lc` 表达式化简为 `e`；`e` 不含控制操作时，有 `(reset (abort e)) = e`。对例三逐步化简：

```racket
(let ([v (reset
           (let* ([x (shift k (k 3))]
                  [y (+ 2 x)])
             (abort y)))])
  (+ 10 v))
;; =>
(let ([v (let ([x 3]) (+ 2 x))])
  (+ 10 v))
```

化简后是普通的 ANF。内层 `(let ([x 3]) (+ 2 x))` 脱糖后就是 `((λ (x) (+ 2 x)) 3)`。`(λ (x) (+ 2 x))` 是等待 `x` 的那段工作，即局部延续。把它命名为 `k`：

```racket
((λ (v) (+ 10 v))
 ((λ (k) (k 3))
  (λ (x) (+ 2 x))))
;; =>
((λ (v) (+ 10 v)) (+ 2 3))
;; => 15
```

取得延续后立即调用，就是普通绑定：`((λ (k) (k e)) (λ (v) body))` 等价于 `(let ([v e]) body)`。

例二不碰 `k`，`shift` 就是 `return`，跳过了加二。末尾的 `abort` 消去后：

```racket
(let ([v (reset
           (let ([x (abort 3)])
             (+ 2 x)))])
  (+ 10 v))
```

舍弃当前局部延续，改把值交给初始局部延续 `values`。`(values 3)` 就是 `3`，于是主体变为 `(λ (_) 3)`：

```racket
> ((λ (v) (+ 10 v))
   ((λ (_) 3)
    (λ (x) (+ 2 x))))
13
```

`(λ (x) (+ 2 x))` 传进来了，主体却没有调用它。前三例到此都是见过的东西：例一和例三是不涉及控制操作的普通计算，例二是延续替换式的提前返回。

回看两份 CPS 的主体。第一份用 `k` 一次：`(λ (k) (k 3))`；第二份不用：`(λ (_) 3)`。和 `shift` 的主体放在一起：

```racket
(shift k (k 3))     ; 主体对应 (λ (k) (k 3))
(shift _ 3)         ; 主体对应 (λ (_) 3)
```

形状完全一致。`shift` 让主体取得局部延续，CPS 把局部延续作为参数交给主体，主体怎样使用它，两种写法保持着相同的结构。

第四例的 `shift` 主体是 `(k (k 3))`，在相同位置又调用了一次 `k`。按照这个对应，CPS 的主体就是 `(λ (k) (k (k 3)))`。消去末尾的 `abort`：

```racket
(let ([v (reset
           (let ([x (shift k (k (k 3)))])
             (+ 2 x)))])
  (+ 10 v))
```

加二延续和外层加十与前两份相同，只有主体不同：

```racket
> ((λ (v) (+ 10 v))
   ((λ (k) (k (k 3)))
    (λ (x) (+ 2 x))))
17
```

前两种主体都把局部延续当作最后一步使用：调用一次交出控制，或者干脆不用。第四例不同：`(k 3)` 不在尾位置，它返回之后，外面还有一次 `(k ...)` 等着用这个结果。同一条局部延续被调用了两次，第一次不是为了交出控制，而是为了拿回一个值继续计算。

这做得到，因为局部延续是普通函数。`(k 3)` 执行加二后正常返回 `5`，等待它的 `(k 5)` 继续得到 `7`。调用者等待答案后的工作由宿主调用帧保存，前文所说的「空出来的程序栈可以承担定界」，就在这个调用位置。

三组 CPS 外层相同，区别只在主体如何使用局部延续。从 CPS 的角度看，三种情况是逐步放宽限制。按前文的 CPS 转换，不涉及控制操作时，必须在*尾位置*使用*当前*局部延续，把每步结果交给它，且*恰好使用一次*：`(shift k (k e)) = (let/lc k e)`、`(let/lc _ e) = e`。支持跳转意味着可以*更换*局部延续，例二就是不用 `k`，改用初始局部延续 `values`：`(values e) = e`、`(shift _ e) = (abort e)`。定界延续则*去掉位置和次数的约束*：局部延续和普通函数一样，任意位置、任意次数都可以使用。`reset/shift` 使 ANF 程序能够取得并自由使用这些局部延续。

上面的 CPS 反复做两件事：`v` 绑定计算结果，`k` 命名等待结果的工作。`let` 给计算结果命名，脱糖后就是 lambda 应用：

| 风格 | 代码                   |
|------|------------------------|
| CPS  | `((λ (v) body) exp)`   |
| ANF  | `(let ([v exp]) body)` |

被命名的也可以是等待结果的工作。普通 `let` 给这个函数命名，`shift` 则在原来的计算位置取得它。以下 `exp`、`body` 指不再含其他控制操作的普通代码片段：

| 风格              | 代码                                     |
|-------------------|------------------------------------------|
| CPS               | `((λ (k) exp) (λ (v) body))`             |
| ANF               | `(let ([k (λ (v) body)]) exp)`           |
| ANF + reset/shift | `(reset (let ([v (shift k exp)]) body))` |

如果边界内已经没有剩余工作，收到什么就交出什么，这个函数就是恒等，即前文的 `values`：

| 风格              | 代码                        |
|-------------------|-----------------------------|
| CPS               | `((λ (k) exp) (λ (v) v))`   |
| ANF               | `(let ([k (λ (v) v)]) exp)` |
| ANF + reset/shift | `(reset (shift k exp))`     |

一个计算可以同时需要输入值和剩余工作。把前面两种绑定放在一起，`v` 接收计算结果，`k` 接收剩余工作：

| 风格              | 代码                                                       |
|-------------------|------------------------------------------------------------|
| CPS               | `((λ (v k) body) exp (λ (w) body1))`                       |
| ANF               | `(let ([v exp] [k (λ (w) body1)]) body)`                   |
| ANF + reset/shift | `(reset (let ([w (let ([v exp]) (shift k body))]) body1))` |

## 规约规则

前面的分析始终与 CPS 实现绑在一起。独立于实现的形式化只需要两条规约规则：

```racket
(reset val)
  => val
(reset E[(shift k expr)])
  => (reset (let ([k (λ (v) (reset E[v]))]) expr))
```

`val` 是值；`E` 是不跨过另一层 `reset` 的求值上下文，`E[v]` 表示把值 `v` 放回 `shift` 所在的位置。第一条：边界内已经是值，直接取出。

第二条是 `shift` 的规约：把 `shift` 到 `reset` 之间的上下文 `E` 取出来，包成函数 `(λ (v) (reset E[v]))` 绑给 `k`，然后在边界内执行 `expr`。规则里有两个 `reset`。

前面用 `shift` 定义了 `let/lc` 和 `abort`；反过来，`shift` 也可以由这两者定义。和第一篇的三种控制运算符一样，`shift` 与 `let/lc` + `abort` 可以互相定义。`shift` 是命名了局部延续的 `return`，用 `let/lc` 命名局部延续，用 `abort` 交出答案：

```racket
(define-syntax-rule (let/lc k body ...)
  (call/lc (λ (k) body ...)))

(define-syntax-rule (shift k expr)
  (let/lc k (let ([v expr]) (abort v))))
```

先计算 `expr` 得到 `v`，再 `(abort v)` 返回。`expr` 在返回前正常计算，仍然在原来的 `reset` 里，所以规约式最外面保留了 `reset`。

内层 `reset` 藏在 `k` 的定义里：`(λ (v) (reset E[v]))`。平凡表示下，局部延续就是普通函数，调用 `k` 就是一次普通的函数调用。CPS 把局部工作搬到堆上的闭包里，空出来的程序栈用于定界，调用 `k` 时分配的新栈帧就是一次新的定界。

`ans` struct 表示下，同一层边界以另一种方式出现。`call/lc` 把捕获的局部延续用 `⊥ᵃ->a` 包一层：调用时沿闭包链执行局部工作，在根部碰到 `a->⊥ᵃ`，`⊥ᵃ->a` 取出答案，和 `anf:eval` 是同一个结构。`⊥ᵃ->a` 的出现就标记了定界。两种表示看到的是同一件事：把 `v` 放回原来的上下文 `E`，在一层新的边界内求值。

# 元延续

前面用 `shift` 定义了 `let/lc` 和 `abort`：一个只捕获，一个只跳转。CPS 世界里 `cps:call/cc` 捕获的延续具有跳转行为，`shift` 能不能也定义 `let/cc`？

要回答这个问题，先得看清定界下的当前延续包含什么。局部延续只到 `values` 为止，而 `values` 是恒等函数，值原样返回。整段局部工作完成或被 `abort` 丢弃之后，这个返回值去了哪里？

回到 `anf:reset` 的定义，`(anf:eval kₐkₐa)` 不在尾位置。Racket 执行它之前，在调用栈上保存了一件工作：拿到返回值后调用 `kₐa`。CPS 计算在边界内以尾调用推进，宿主栈不会随局部工作增长；但边界本身是非尾调用，`anf:reset` 留下的等待帧保存了外层的 `kₐa`。内层计算完成后，得到的 `a` 通过普通返回抵达这一帧，`(kₐa a)` 开始执行。四个例子中外层的加十，就是这样等到的。

边界内任意位置的剩余工作因此分成两部分：从当前位置沿闭包链到 `values` 的局部延续，和边界之外等待局部答案的外层工作。后者由宿主调用栈保存，称为**元延续**（meta-continuation）。正常执行时，值沿闭包链经过每一步局部工作，到达 `values`，通过普通返回交给元延续。完整的延续是两者的复合：

$$延续 = 元延续 ∘ 局部延续$$

`abort` 和 `let/lc` 恰好各自对应其中一部分。`abort` 把值送到边界之外，就是当前的元延续；`let/lc` 取得当前局部延续 `k`。代入这两个部件，当前延续就是 `(∘ abort k)`：

```racket
(define (call/cc proc)
  (let/lc k (proc (∘ abort k))))
```

注意，`k` 还是之前捕获的局部延续，但调用 `abort` 就是调用当前的元延续，不是捕获 `k` 时的元延续。把捕获和调用放在不同的 `reset` 里，差异就显现出来了：

```racket
> (let ([k (reset
            (let ([x (let/cc k (abort k))])
              (+ x 2)))])
    (+ (reset (k 3)) 100))
105
```

第一个 `reset` 里 `let/cc` 捕获当前延续后，`(abort k)` 把它作为答案交出。`k` 携带的局部工作是加二。第二个 `reset` 里调用 `(k 3)`，展开为 `(abort (k 3))`：`k` 执行加二得到 `5`，`abort` 把 `5` 送出当前的边界，即第二个 `reset`。边界外的加一百正常执行，得到 `105`。

当然，如果捕获和调用时最近的边界都是同一次 `reset` 调用建立的边界，那么边界外等待的工作便是同一份，调用时的元延续就是捕获时的元延续。

上面比较的是边界外的工作。再看边界以内：`let/cc` 交出的延续 `(∘ abort k)`，比 `let/lc` 捕获的局部延续 `k` 多了一层 `abort`。如果这个延续在某个 `reset` 的尾位置调用，调用结果之外没有局部工作需要丢弃，外层的 `reset` 会消去这层 `abort`：

```racket
  (reset ((∘ abort k) v))
= (reset (abort (k v)))
= (reset (k v))
```

因此，如果 `let/cc` 捕获的延续只在 `reset` 的尾位置调用，就可以改用 `let/lc` 只捕获局部延续。第一篇的 `(label)` 可以写成 `(let/cc k k)`；阴阳谜题中的延续恰好只在这样的尾位置调用。把它们换成局部延续：

```racket
> (reset
   (let ([kn (let/lc k0 k0)])
     (display #\@)
     (let ([k (let/lc kn+1 kn+1)])
       (display #\*)
       (kn k))))
@*@**@***@****@...
```

输出不变。`kn` 和 `k` 仍是会正常返回的局部延续，并没有跳转能力；只不过每次调用它们时，`abort` 原本要丢弃的局部工作都是空的。

## 栈的切片

第二篇把延续写成了闭包链。相邻两处的延续只差一步，`(neg f)` 把后一处的 $kq$ 变成前一处的 $kp = kq ∘ f$；从初始延续开始一步步接上去，每一处的延续都是一个具体的元素。

拿四个例子里 `x` 的位置来看。把加二的 `(λ (x) (+ 2 x))` 记作 `add2`，加十的 `(λ (v) (+ 10 v))` 记作 `add10`，整个程序之后的延续记作 `k`。这一处的延续是 `(∘ k add10 add2)`：先加二，再加十，最后交给 `k`。`reset` 的边界落在加二与加十之间，沿着它把链切开：

```racket
  (∘ k add10 add2)
= (∘ (∘ k add10) add2)
```

右边一段 `add2` 是边界以内的工作，`shift` 在这里取得的局部延续就是它。左边一段 `(∘ k add10)` 是边界以外等着答案的工作，也就是元延续。

一般的情形也是这样切。把局部计算的答案类型记为 $a$，$kq$ 沿边界分成两段：局部延续 $kₐq : q → a$ 执行边界内的工作，产出答案；元延续 $ka : a → ⊥$ 接过答案，继续边界外的工作。$ka$ 在 $𝒟$ 里写不出来，它就是由宿主调用栈保存的那部分工作。$kq = ka ∘ kₐq$，对应到栈上就是两段首尾相接。

把分解代入 $kp = kq ∘ f$：

```racket
  kp
= (∘ kq f)
= (∘ (∘ ka kₐq) f)
= (∘ ka (∘ kₐq f))
= (∘ ka kₐp)
```

$ka$ 不变，新增的工作落在局部这一段。$kₐq ∘ f$ 先执行 $f$，再执行原有的局部工作 $kₐq$，结果仍然到达共同出口 $a$。等待 $p$ 的新局部延续就是 $kₐp = kₐq ∘ f : p → a$。

不同位置的局部延续等待不同的输入，却以 $a$ 为共同终点。「局部延续」一节的换基，在栈上就是这样一刀：完整延续以 $⊥$ 为基，在边界处切开，边界以内的一段以 $a$ 为基，元延续 $ka$ 再把它接回 $⊥$。每个 $kₐp$ 都是 $¬ₐp = p → a$ 的一个元素，这就是局部否定。

走到边界处，局部已经没有剩余工作，收到答案原样交出，完整的剩余工作就是 $ka ∘ idₐ = ka$。这正是 `values` 所在的位置。平凡表示下 $⊥ᵃ = a$，初始局部延续 `a->⊥ᵃ` 就是 $idₐ : a → a$，$¬ₐa$ 的一个元素。`anf:eval` 每次启动嵌入计算，把它作为栈底交给内层，局部链从这里逐层预复合，长出各个位置的具体延续。

在这幅图景中，整个程序在操作系统眼里也有同样的结构。操作系统交给程序一个空栈，初始延续是 `exit`，程序是一段返回 `Byte` 类型答案的局部计算。`values` 对局部计算而言，和 `exit` 对整个程序一样：标记这一层已经没有剩余工作。

# 局部否定下的世界

第二篇中，$¬$ 之间的反向箭头构成了逆否世界 $𝒰$。基换成 $a$ 以后，$¬ₐ$ 之间的反向箭头同样构成一个世界。本篇的代码都在 $𝒟$ 中，第二篇的 `←` 在这里写作 `←𝒟`：

```racket
(define-type (←𝒟 q p) (→𝒟 p q))
(define-type (→𝒰ₐ p q) (←𝒟 (¬ₐ p) (¬ₐ q)))

(: neg (∀ (p q) (→ (→𝒟 p q) (∀ (a) (→𝒰ₐ p q)))))
(define ((neg f) kₐq) (∘ kₐq f))
```

`neg` 把 `f` 接在已有的局部延续前面，沿用那份工作的终点，并不关心终点是什么，所以 `(neg f)` 对任意答案类型 $a$ 都成立。

第二篇里，`neg` 只作用在普通函数上：延续 $p → ⊥$ 在 $𝒟$ 中写不出来，没法交给 `neg`。

局部延续不同。「边界中的边界」取了平凡表示之后，局部空 $⊥ᵃ$ 就是普通类型 $a$，局部否定 $¬ₐp = p → ⊥ᵃ$ 也就只是普通的函数类型 $p → a$。局部延续就是普通函数，`neg` 的参数当然也可以是局部延续。

把 `f` 换成 $kₐp$、$q$ 换成 $a$，`(neg kₐp)` 仍是一支从 $p$ 指向 $⊥ᵃ$ 的箭头，只不过住在逆否世界里。用局部否定改写 `neg` 的类型：

```racket
(define-type ⊥ˣ x)
(define-type (¬ₓ𝒰ₐ p) (→𝒰ₐ p ⊥ˣ))

(: neg (∀ (p a) (→ (¬ₐ p) (∀ (x) (¬ₐ𝒰ₓ p)))))
```

局部否定带两个下标：左下标是否定的基，也就是局部延续的终点；右下标是它所在世界的基。

控制运算符把当前局部延续提升后交给程序。当前局部延续落在自己的局部空 $⊥ᵃ$ 上，而 $⊥ᵃ$ 就是当前世界的答案 $a$。否定的基与世界的基重合，取 $x = a$，就得到 `neg:call/lc`：

```racket
(: neg:call/lc (∀ (p a) (→𝒰ₐ (→𝒰ₐ (¬ₐ𝒰ₐ p) p) p)))
(define ((neg:call/lc kₐp) neg:proc) ((neg:proc kₐp) (neg kₐp)))
```

程序拿到的 `(neg kₐp)` 是一个映射：给它一条等待 $a$ 的延续，它把保存的局部工作接在前面。调用它，局部工作执行完毕后正常返回，当前延续接着运行。

`call/cc` 交出的延续不接在当前延续前面，而是丢弃当前延续。按元延续一节的分解，调用它时，保存的局部工作做完，答案越过边界交给当时的元延续，一直走到整个程序的出口。从局部计算内部看，那里没有任何值能够返回，是全局的空 $⊥$。取 $x = ⊥$，得到的是 $𝒰ₐ$ 中指向 $⊥$ 的否定，形状与第二篇的 $¬𝒰$ 相同：

```racket
(define-type (¬𝒰ₐ p) (→𝒰ₐ p ⊥))
```

展开是 `(←𝒟 (¬ₐ p) (¬ₐ ⊥))`，一个从 $¬ₐ⊥ = ⊥ → a$ 到 $¬ₐp$ 的函数。它收到的参数是调用处的延续，等待一个 $⊥$ 类型的结果。这个参数和第一篇的 `absurd` 一样，虽然是函数，却永远无法调用：没有 $⊥$ 类型的值可以交给它。它不能参与任何计算，只能丢弃。`neg*` 正是这样做的，忽略参数，直接交出手中的 $kₐp$：

```racket
(: neg* (∀ (p a) (→ (¬ₐ p) (¬𝒰ₐ p))))
(define ((neg* kₐp) _k) kₐp)
```

用 `neg*` 代替 `neg`，得到 `call/cc`：

```racket
(: neg:call/cc (∀ (p a) (→𝒰ₐ (→𝒰ₐ (¬𝒰ₐ p) p) p)))
(define ((neg:call/cc kₐp) neg:proc) ((neg:proc kₐp) (neg* kₐp)))
```

两个控制运算符保存的是同一份局部工作 $kₐp$。`call/lc` 交出的延续，调用时把这份工作接在当前延续前面，完成后正常返回；`call/cc` 交出的延续，调用时丢掉当前延续，只留下这份工作。

两个类型只差否定的基：`call/lc` 取 $x = a$，`call/cc` 取 $x = ⊥$。把 $𝒰ₐ$ 的箭头读作蕴含，$(¬ₓp → p) → p$ 展开是 $((p → x) → p) → p$，正是第一篇的 Peirce 律，只是 $q$ 换成了 $x$；$x = ⊥$ 时，它就是 Clavius 律。第一篇中，借助 `absurd`，两条定律在操作上没有区别。在这里它们分开了：延续落在当前的基 $a$ 上时会回到调用处，落在 $⊥$ 上时不会。

这些构造可以搬到 CPS 世界。第二篇的 `flip` 对任意两层柯里化函数都成立，基换成 $a$ 也不例外，仍然在逆否与 CPS 两种写法之间来回：

```racket
(define-type (→𝒦ₐ p q) (→𝒟 p (¬ₐ¬ₐ q)))
(define-type (¬ₓ𝒦ₐ p)  (→𝒦ₐ p ⊥ˣ))
(define-type (¬𝒦ₐ p)   (→𝒦ₐ p ⊥))

(: flip  (∀ (p q) (→ (→𝒰ₐ p q) (→𝒦ₐ p q))))
(: flip¹ (∀ (p q) (→ (→𝒦ₐ p q) (→𝒰ₐ p q))))
```

`neg` 和 `neg*` 分别经 `flip` 得到 `cps` 和 `cps*`，局部延续的写法也一起带了过来：

```racket
(: cps  (∀ (p q) (→ (→𝒟 p q) (→𝒦ₐ p q))))
(: cps  (∀ (p a) (→ (¬ₐ p) (∀ (x) (¬ₐ𝒦ₓ p)))))
(: cps* (∀ (p a) (→ (¬ₐ p) (¬𝒦ₐ p))))
(define cps  (∘ flip neg))
(define cps* (∘ flip neg*))
```

将交给程序的延续，以及接收它的程序，都换成 CPS 写法：

```racket
(: cps:call/lc (∀ (p a) (→𝒦ₐ (→𝒦ₐ (¬ₐ𝒦ₐ p) p) p)))
(: cps:call/cc (∀ (p a) (→𝒦ₐ (→𝒦ₐ (¬𝒦ₐ p) p) p)))

(define ((cps:call/lc cps:proc) kₐp) ((cps:proc (cps  kₐp)) kₐp))
(define ((cps:call/cc cps:proc) kₐp) ((cps:proc (cps* kₐp)) kₐp))
```

## 求值与边界

上面的控制运算符在 `anf:` 宏编译出的编码中使用。编码带有类型 $¬ₐ¬ₐp = (p → a) → a$，是等待局部延续 $¬ₐp$ 的嵌入程序。解释器为嵌入程序 $¬ₐ¬ₐa$ 提供初始局部延续 `a->⊥ᵃ`，类型为 $¬ₐa$，得到答案 $a$：

```racket
(: a->⊥ᵃ (∀ (a) (¬ₐ a)))
(define a->⊥ᵃ values)

(: anf:eval (∀ (a) (→ (¬ₐ¬ₐ a) a)))
(define (anf:eval kₐkₐa) (kₐkₐa a->⊥ᵃ))
```

`anf:eval` 交进去 `a->⊥ᵃ`，得到嵌入程序的答案。第二篇中终点是 $⊥$，初始*延续* $¬a$ 需要借助宿主实现跳转。这里普通结果类型与答案类型都是 $a$，初始局部延续 $¬ₐa = a → a$ 就可以由恒等函数 `values` 提供，无须借助宿主跳转。

`anf:eval` 从 $¬ₐ¬ₐa$ 得到 $a$，本身也是一条局部延续，类型可以写成 $¬ₐ(¬ₐ¬ₐa)$，即三重局部否定。`a->⊥ᵃ` 是单重否定 $¬ₐa$。`cps` 将恒等函数 `values` 提升为双重否定引入 `cps:id`，包装 `a->⊥ᵃ` 后得到三重否定：

```racket
(: cps:id (∀ (p a) (→ p (¬ₐ¬ₐ p))))
(define cps:id (cps values))

(: anf:eval (∀ (a) (¬ₐ¬ₐ¬ₐ a)))
(define anf:eval (cps:id a->⊥ᵃ))
```

`anf:eval` 本身就是一条以 $a$ 为基的局部延续，按 `cps` 作用于局部延续时的类型，经 `cps` 提升后对任意 $x$ 都成立：

```racket
(: anf:reset (∀ (a) (→ (¬ₐ¬ₐ a) (∀ (x) (¬ₓ¬ₓ a)))))
(define anf:reset (cps anf:eval))
```

内层的答案类型是 $a$，提升后可以处在任意答案类型 $x$ 的 CPS 世界中。展开定义：

```racket
(define ((anf:reset kₐkₐa) kₓa)
  (kₓa (anf:eval kₐkₐa)))
```

`anf:eval` 把 `values` 交给内层，运行得到答案 $a$。外层延续 $kₓa : a → x$ 接过这个值，继续自己的工作。同一个值在内层已经是答案，越过边界后变成普通结果。内层从恒等函数开始积起局部工作，外层等待它交出答案，这正是栈的切片中看到的边界。`anf:reset` 的类型把两侧分别写了出来：内层以 $a$ 为基，外层以 $x$ 为基，每次 `reset` 都在边界处换一次基。

# 否定翻译与 A-翻译

上一节交入恒等函数就启动了编码。不过，本篇开头改变的不只是终点 $⊥$：`Real` 也变成了 `Realᵃ`，普通结果之外多了一条答案路径。

对任何原子结果类型 $p$，这个变化都可以写成 $pᵃ = p ∨ a$。$⊥$ 没有普通值，$⊥ᵃ = ⊥ ∨ a$ 便只剩答案分支，在标签表示中由 `(Ans a)` 表示。箭头类型的输入与输出各自递归翻译。这种以答案类型 $a$ 为参数的操作，叫做 **A-翻译**（A-translation）。

第二篇把原子结果类型 $p$ 的计算编码为双重否定 $(p → ⊥) → ⊥$。对它做 A-翻译，$p$ 变成 $pᵃ$，$⊥$ 变成 $⊥ᵃ$：

$$(p → ⊥) → ⊥ \quad⟼\quad (pᵃ → ⊥ᵃ) → ⊥ᵃ$$

右侧的计算等待一个 $pᵃ → ⊥ᵃ$ 的函数。$pᵃ$ 是 $p ∨ a$，交给这个函数的可能是普通值，也可能是提前到来的答案，两种情况都要有去处。处理一个「或」，就是两种情况各给一个函数：

$$(p ∨ a) → ⊥ᵃ \quad=\quad (p → ⊥ᵃ) ∧ (a → ⊥ᵃ)$$

所以翻译之后，计算等待的是两个局部延续：一个 $¬ₐp$ 接普通值，一个 $¬ₐa$ 接提前到来的答案。把 `mul` 照这个样子写出来，前一个叫 `kₐ`，后一个叫 `iₐ`：

```racket
(: mul (→ Real * Real))
(define (mul . r*)
  (: loop/ki (→ (Listof Real) (¬ₐ Real) (¬ₐ Real) ⊥ᵃ))
  (define (loop/ki r* kₐ iₐ)
    (if (null? r*)
        (kₐ (*))
        (let ([r (car r*)])
          (if (zero? r)
              (iₐ r)
              (loop/ki (cdr r*) (λ (v) (kₐ (* v r))) iₐ)))))
  (loop/ki r* a->⊥ᵃ a->⊥ᵃ))
```

```racket
> (mul 1 2 3 4)
24
> (mul 1 2 0 3 4)
0
```

乘到头，结果交给 `kₐ`；遇到零，答案交给 `iₐ`。两个延续的待遇不一样。`kₐ` 每递归一层就在前面接上一步乘法。`iₐ` 原样传下去，从头到尾都是开始时交进来的那一个，也就是初始局部延续 `a->⊥ᵃ`。第二篇尾递归的 `fact/k` 也是这样原样传递 `k` 的。

从不改变的参数，不必当参数传。去掉 `iₐ`，把 `(iₐ r)` 直接写成 `(a->⊥ᵃ r)`，剩下的就是「局部延续」一节的 `loop/kₐ`。翻译之后要两个延续，本篇的代码却一直只传一个，原因在这里：另一个是固定的。它在一段局部计算之内不变，`reset` 开启新的一段时，`anf:eval` 才交进来新的一个。

计算于是只等待 $kₐ : p → ⊥ᵃ$，类型成为 $(p → ⊥ᵃ) → ⊥ᵃ$。再取已经用过的平凡表示 $⊥ᵃ = a$，便得到 $(p → a) → a = ¬ₐ¬ₐp$，正是本篇使用的局部编码。两条路径分别落在 `cps` 与 `cps*` 上：`cps` 把结果交给当前延续；`cps*` 丢弃当前延续，改用手里保存的那一个，`cps:abort` 就是 `(cps* a->⊥ᵃ)`，把值交给被省掉的初始局部延续。

开头不带延续的 `mul` 走的也是这两条路，只是合在了一个值里。把两个延续合回一个处理 $pᵃ$ 的函数，`iₐ` 既已固定，答案那一支就是原样交出：

```racket
(λ (v) (if (ans? v) v (kₐ v)))
```

`loop` 正是这样做的：收到 `ans` 就原样传递，否则继续计算。

当普通结果类型也为 $a$ 时，两个延续类型相同，启动时交进去的是同一个，上面的 `(loop/ki r* a->⊥ᵃ a->⊥ᵃ)` 就是这样。这时编码等待的是 $a → a$，恒等函数就能充当初始局部延续。上一节的 `anf:eval` 所提供的，正是这个类型的元素。第二篇启动计算时需要借用 `raise` 的位置，现在由普通函数填上，解释器也在 $𝒟$ 中完成。

一般的 $¬¬p → p$ 并没有因此在 $𝒟$ 中成立。这里运行的是答案类型已经改变的局部编码，且求值处的普通结果类型与答案类型恰好吻合。两种翻译与答案分支的处理，把原来的编码接到了这个可以直接求值的类型上。

# 总结

`mul` 遇到零时，答案已经确定，剩余的乘法不必继续。`goto` 通过跳转越过这些工作，`Ans` 则把同一件事写成了答案的传播：普通值继续计算，已经得到的答案原样交出。提前返回，由此成为普通函数能够表达的行为。

两种翻译分别处理了这条路径上的两个问题。否定翻译把经典控制翻译成构造性宿主中的延续编码，剩余工作成为显式参数；但第二篇的解释器在启动时，仍需借用宿主的跳转。A-翻译为计算增加答案路径，使提前结束计算可以表示为产生并交出一个局部答案。在本篇的 CPS 实现中，不调用当前延续就跳过了那份剩余工作，直接返回答案就结束了这段局部计算。控制转移，在这里成了嵌入程序对自己参数的取舍。

被跳过的工作仍然是一个普通函数，可以保存下来，在需要时调用。它的执行范围由边界限定，完成后正常返回，边界外等待的工作则由元延续保留。结果类型与答案类型吻合时，恒等函数就能充当初始局部延续，解释器也由普通函数构成。第二篇完成了经典控制的编码，本篇补上了从编码到求值的缺口。

回头看本篇的代码，这些构造所需的东西少得出奇。`flip` 的输入里带着 $¬ₐ$，先固定答案类型 $a$，再用 `→𝒟` 和 `←𝒟` 写出三个运算，以及它们反过来的读法：

```racket
(: neg   (∀ (p q) (→ (→𝒟 p q) (←𝒟 (¬ₐ p) (¬ₐ q)))))
(: neg¹  (∀ (q p) (→ (←𝒟 q p) (→𝒟 (¬ₐ q) (¬ₐ p)))))

(: cps   (∀ (p q) (→ (→𝒟 p q) (→𝒟 p (¬ₐ¬ₐ q)))))
(: cps¹  (∀ (q p) (→ (←𝒟 q p) (←𝒟 (¬ₐ¬ₐ q) p))))

(: flip  (∀ (p q) (→ (←𝒟 (¬ₐ p) q) (→𝒟 p (¬ₐ q)))))
(: flip¹ (∀ (p q) (→ (→𝒟 p (¬ₐ q)) (←𝒟 (¬ₐ p) q))))
```

`neg` 给箭头两端各套一层 $¬ₐ$，方向掉头；`cps` 给箭头所指的一端套上 $¬ₐ¬ₐ$，方向不变；`flip` 把 $¬ₐ$ 从一端挪到另一端，方向掉头。带上标的是同一段代码反过来的读法。

三组并不独立。有了 `neg`，`cps` 和 `flip` 就可以互相得到。先用 `neg` 给两端套上 $¬ₐ$ 并掉头，再用 `flip` 把左端的 $¬ₐ$ 挪到右端、掉头回来：左端复原，右端多出 $¬ₐ¬ₐ$，这正是 `cps = (∘ flip neg)`。反过来，由 `neg` 和 `cps` 也能写出 `flip`，这是第二篇留下的练习。

内层走到了世界尽头，外层只是收到了一次函数调用的结果。

## 未解的线索

对应表的每一组是同一个程序的几种写法，写法之间的转换是机械的，一个程序应当能够自动执行这个转换。但这样的程序在每一步也会积累自己的剩余工作，也有自己的延续。而它在某一点的剩余工作，所描述的恰好是目标程序在同一点的剩余工作。一条在构建程序，一条在执行程序，追踪的是同一份计算。
